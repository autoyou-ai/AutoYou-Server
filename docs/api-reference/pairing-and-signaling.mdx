# Pairing & WebRTC Signaling APIs

These routes coordinate device authentication and the signaling exchange that opens an encrypted WebRTC link. How pairing works, and how the modes differ, is explained in [Pairing & Device Discovery](/architecture/pairing-and-discovery) and [Security Modes](/security/security-modes). Every route is listed in the [route catalog](/api-reference/route-catalog).

---

## Secure pairing handshake (admin app)

Local Pair and Auto Pair share a two-step handshake in Secure and Secure Professional modes. The bodies are not JSON: they are the text of the password-authenticated key exchange messages (`shared/pairing_cpace.py`), and the offer in the second step is encrypted under the key the first step established.

| Route | Purpose |
| :--- | :--- |
| `POST /api/autopair_hello` | The first step. Success returns the handshake answer as plain text; a failure returns `{"error": "..."}` with `400`. |
| `POST /api/autopair` | The second step. Submits the encrypted WebRTC offer and returns the encrypted answer. Plaintext offers are rejected in the secure modes. |

Details that matter when you call them:

- **Identity.** The pairing identity comes from the `session_id` query parameter or the `X-AutoYou-Session-Id` header, and the client platform from `X-AutoYou-Platform`. Both steps must use the same identity so the second step finds the key the first established.
- **No sign-in needed on the private network.** The handshake proves the server password without sending it, so a caller on this computer or the private network needs no admin session. A caller from elsewhere without a session is refused.
- **Rate limits.** Repeated attempts return `429` with "Too many pairing attempts."; a pairing subsystem that is not ready returns `503`.
- **Bluetooth.** A Bluetooth pairing platform is refused unless Bluetooth pairing is enabled.

## OTP and signaling (auth app)

One-time-code pairing, `POST /auth`, and the `/signal/{session_id}` routes are served by the auth app on port `8002`. They are described in the [auth app reference](/api-reference/auth-app). Offers, answers, and trickled ICE candidates travel through them.

---

## Local pair information

`GET /api/local-pair-info` returns the connection details a phone on the same network needs: `addresses`, `primary_address`, `port`, `bind_host`, `loopback_only`, `lan_reachable`, `server_name`, and `success`. It needs an admin sign-in, and it emits no discovery traffic.

---

## Setup QR code

`GET /api/settings/export-qr` returns a QR code for one-scan configuration of a supported mobile app. It needs an admin sign-in.

<Warning>
The QR payload is not encrypted and contains the server password and the shared authenticator secret. Anyone who scans it can pair with the server. See [Pairing & Device Discovery](/architecture/pairing-and-discovery#setup-qr-code-automatic-configuration) for its fields.
</Warning>

## Live Pair

These routes need an admin sign-in and drive the QR-based pairing in the admin console.

| Route | Purpose |
| :--- | :--- |
| `GET /api/live-pair/status` | The current live-pairing state, with QR frames to display |
| `POST /api/live-pair/scan` | Decode a QR code from a JPEG camera frame (`data:image/jpeg;base64,...`, up to about 2 MB). Needs OpenCV. |
| `POST /api/live-pair` | Submit a pairing message (up to 70,000 bytes) and receive the result, the response text, and QR frames |
| `GET /api/bluetooth-pairing/status` | The state of Bluetooth pairing |
